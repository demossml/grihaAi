## 1. Executive Summary

Память «Гриши» — собственная реализация `SqliteRagMemoryService` (better-sqlite3 + FTS5 + sqlite-vec + гибридный RRF-ранжировщик). Это рабочая, консистентная система: WAL, busy_timeout 5000, транзакции, триггеры синхронизации FTS, 0 ошибок SQLITE_BUSY/LOCKED в конкурентных тестах (до 5 писателей / 20 читателей в одном процессе). Пиковая латентность гибридного поиска: **0.59 мс @ 1k, 8.7 мс @ 10k, 57.6 мс @ 50k, 125.2 мс @ 100k** записей — брутфорс-скан векторов, но «достаточно быстро» вплоть до 100k на M5 Pro.

Ключевые измеренные слабости:

1. **Семантический recall низкий, но это свойство хеш-эмбеддингов, а не архитектуры.** Recall@5 semantic = 0.20 (фолбэк без HTTP-эмбеддингов). С реальным эмбеддинг-сервисом значение НЕ ИЗМЕРЯЛОСЬ — NOT TESTED (см. §18).
2. **Нет времени, важности и уверенности в ранжировании.** Противоречивые факты: 50/50 пар — «старший» факт всегда выше «нового». Запросы на естественном языке с несовпадением токенов (AND-конъюнкция FTS + LIKE-фолбэк) дают **0 результатов**: contradiction recall = 0.
3. **Нет дедупликации** (1/5/100 одинаковых записей → 1/5/100 строк) и **нет delete/update API** (удаление только сырым SQL).
4. **FTS занимает 92% размера БД** (20.5 МБ из 22.3 МБ на 10k записей; 204.7 МБ из 222.3 МБ на 100k).
5. **Один битый embedding-BLOB ломает весь векторный запрос**, а malformed-metadata ломает чтение (`JSON.parse` без защиты).

Вывод: **полная миграция на любой кандидат экосистемы sqlite-ai не оправдана** измеренными данными. Приоритет — точечные исправления текущего сервиса (реальные эмбеддинги → semantic recall; recency-коэффициент; delete/dedup API; защитные try/catch). Решение за владельцем — дерево решений в §17.

## 2. Текущая архитектура

Пайплайн памяти (как он есть):

```
ПОЛЬЗОВАТЕЛЬ → СООБЩЕНИЕ → ЗАПИСЬ В ПАМЯТЬ (addFact/addMessage/addInsight)
  → NORMALIZATION: ❌ НЕТ (факт сохраняется как есть)
  → CHUNKING: ❌ НЕТ (одна запись = один факт целиком)
  → EMBEDDING: HashingEmbeddingService (лексический) | HttpEmbeddingService (если cfg.embedding.model+apiKey)
  → ХРАНЕНИЕ: SQLite (facts + facts_fts FTS5 external-content + embedding BLOB)
  → ИНДЕКСЫ: FTS5 (триггеры ai/ad/au) + sqlite-vec (без ANN-индекса — полный скан)
  → ПОИСК: FTS-branch + vector-branch → RRF k=60
  → РАНЖИРОВАНИЕ: только bm25 / 1−cos / RRF. Без recency, importance, confidence
  → CONTEXT BUILDER → LLM
```

Стадий нормализации и чанкинга **не существует** — каждый факт пишется «как сказано». Это осознанная модель «structured state» (короткие атомарные факты), не markdown-корпус.

## 3. Текущая модель данных

| Сущность | Таблицы | Поля фактов | Примечание |
|---|---|---|---|
| facts | `facts`, `facts_fts` | id, content, category, project_id, agent_id, bot_id, created_at, updated_at, metadata TEXT, embedding BLOB | нет delete/update API; нет UNIQUE; нет recency/confidence |
| messages | `messages`, `messages_fts` | session_id, role, content | поиск по сессиям через searchSessions |
| insights | `insights`, `insights_fts` | аналог facts | addInsight/searchInsights |

Разделение «memory vs structured state»: память = свободные факты; structured state = отдельные таблицы приложения (в prod-БД это `user_profiles`, `client_notes`, `cron_jobs` и т.д.). В prod-БД `~/.grish-ai/memory.sqlite` таблицы RAG-памяти (`facts`, `messages`, `insights`) **пустые** (0 строк), при этом `client_notes` = 40 строк — память фактически ещё не наполнялась в проде.

## 4. Текущий retrieval-пайплайн (формулы)

- FTS-ветка: `ORDER BY -bm25(facts_fts) DESC` — запрос строится как конъюнкция `"токен"* AND "токен"*` (все токены обязаны встретиться).
- LIKE-фолбэк (если FTS вернул < limit): `content LIKE '%query%'`, константный скор `1.0`, сортировка `updated_at DESC`.
- Векторная ветка: `1 - vec_distance_cosine(embedding, q)` (sqlite-vec) или JS `cosineSimilarity` при недоступном расширении.
- Гибрид: **Reciprocal Rank Fusion, k=60**: $\text{score} = \sum_{sources} \frac{1}{60 + rank_{source} + 1}$, сортировка по убыванию, `source ∈ {hybrid, vector, fts}`.
- Ограничения: `clampLimit` 1..50 (default 10); **порогов (min_score) нет**; recency/importance/confidence **нигде не участвуют**.

## 5. SQLite-аудит (интроспекция)

PRAGMA (фактические): `journal_mode=wal`, `synchronous=1` (NORMAL), `busy_timeout=5000`, `cache_size=-16000` (16 МБ), `page_size=4096`, `auto_vacuum=0`, `mmap_size=0`.

EXPLAIN QUERY PLAN:
- FTS: `SCAN facts_fts VIRTUAL TABLE INDEX 0:M1` + `SEARCH f USING INTEGER PRIMARY KEY` + `USE TEMP B-TREE FOR ORDER BY`.
- Vector: `SCAN facts` + `USE TEMP B-TREE FOR ORDER BY` — **полный брутфорс-скан таблицы**, ANN-индекса нет. Это не дефект, а цена за отсутствие преиндексации.

Prod-БД `~/.grish-ai/memory.sqlite` найдена и прочитана только на чтение: `user_profiles=1`, `client_notes=40` (+FTS 40), `facts/messages/insights=0`.

## 6. Методология бенчмарков

Весь инструментарий — изолированный `tools/memory-audit/` (не входит в tsconfig, в production не импортируется). Тесты гоняются на временной БД `/tmp/griha-memory-audit/memory.sqlite` через **реальный** `SqliteRagMemoryService` (не мок): вставка через `addFact` (реальные триггеры FTS, реальные BLOB-эмбеддинги), даты проставляются сырым SQL. Метрики: Recall@1/5/10, MRR, Precision@5/10, nDCG@10; латентность avg/p50/p95/p99.

- Сценарий «PostgreSQL (январь) → SQLite (сентябрь)»: на запрос «What database does the user currently use?» топ-2 = `[A(jan-postgres), B(sep-sqlite)]` — **старый факт выше нового**. Времени в скоре нет.
- Противоречия: 50/50 пар — 0 «newer-first», 50 «older-first». Нет отношения supersedes, нет детекции противоречий, нет confidence.

Ключевые факты о кандидатах:

- **sqlite-memory** — markdown-файлы как source of truth: md4c-парсер с markdown-aware чанкингом, гибрид vector+FTS5 с настраиваемыми весами (`vector_weight`, `min_score`, `search_oversample`), контент-хэш дедупликация (`memory_add_text` пропускает дубли), **delete API** (`memory_delete`, `memory_delete_context`, `memory_clear`), deferred-embeddings, CRDT-синк через sqlite-sync. - **sqlite-rag** — Python CLI поверх sqlite-ai + sqlite-vector, RRF-фьюжн, recursive character splitter, PDF/DOCX. Для TS-монорепо — только через subprocess; без лицензионного файла и с Elastic-зависимостями — юридически непригоден как есть.
- **sqlite-vector** — «no virtual tables, BLOB в обычных таблицах», SIMD, квантование INT8/TurboQuant, без преиндексации. Их собственный бенчмарк (та же машина M5 Pro): 1M×768 cosine — 484 мс/query FLOAT32 exact; INT8 preloaded 37.6 мс @ 99.5% recall. Лицензия — стоп-фактор для закрытого продакшена.
- **sqlite-ai** — on-device LLM/эмбеддинги/whisper/vision из SQL (GGUF, Metal/CUDA). Для локальных эмбеддингов привлекателен, но Elastic 2.0: production требует коммерческой лицензии.
- **sqlite-vec** (уже используется) — brute-force `vec0`, float/int8/binary, pre-v1 («expect breaking changes»). Уже загружается в каждом соединении сервиса.

## 17. Риски

1. **CRITICAL — пустой ответ на естественно-языковые запросы.** AND-конъюнкция FTS + substring-LIKE ⇒ запрос «What database does the user currently use?» возвращает 0. Если LLM формулирует поиск вопросительно — память «слепнет» (contradiction recall = 0).
2. **HIGH — устаревшие факты вытесняют актуальные** (50/50 пар; нет recency/supersedes).
3. **HIGH — семантика зависит от внешнего embedding-сервиса.** Без `cfg.embedding` — лексический хеш (semantic recall 0.2@5). С сервисом — сетевая зависимость (не измерена).
4. **HIGH — 1 битый BLOB ломает весь векторный поиск** (нет try/catch вокруг vec-запроса).
5. **MEDIUM — рост FTS-индекса** (92% БД; 222 МБ на 100k).
6. **MEDIUM — нет delete API** ⇒ GDPR/исправление ошибок только сырым SQL; **нет дедупликации** ⇒ повторные записи раздувают индекс и размывают топ-1 (near-dup R@1 = 0.02).
7. **MEDIUM — malformed metadata** ломает чтение записи.
8. **LOW — sqlite-vec pre-v1** — возможны breaking changes; загрузка расширения на каждое соединение — точка отказа (уже обёрнута в try/catch с JS-фолбэком).
9. **LOW — масштаб:** линейный брутфорс 126 мс @ 100k; на 1M — минуты (не измерено).

## 19. Дерево решений (владельцу; измеренные факты, не рекомендация-приказ)

```
Есть ли реальный embedding-сервис в проде?
├── НЕТ → IF semantic recall важен: включить cfg.embedding (код уже поддерживает)
│        ELSE оставить как есть, зафиксировав recall=0.2@5 как предел фолбэка
└── ДА  → перемерить semantic recall (§18)
          IF R@5 < 0.7  → тюнинг формулы поиска (OR-запросы, веса, oversample)
          IF R@5 ≥ 0.7  → текущая архитектура достаточна

Корпус фактов:
├── < 10k → текущий брутфорс-скан оптимален (8.7 мс)
├── 10k–100k → приемлемо (до 126 мс); мониторить
└── > 100k (или p95 > SLO) → рассмотреть индекс векторов:
     ├── остаться на sqlite-vec + кэш/пагинация (MIT) — нулевой лицензионный риск
     ├── sqlite-vector INT8 (M5 Pro: 37.6 мс/1M, recall 99.5%) — НО Elastic 2.0: закрытый prod → коммерческая лицензия
     └── внешний ANN-сервис — вне скоупа этого аудита

Нужна ли актуальность (recency)?
├── ДА → добавить временной коэффициент в RRF-скор (маленькое изменение ранжировщика)
└── НЕТ → зафиксировать «архивная память» как дизайн-решение

Нужны ли delete/update и дедупликация?
├── ДА → доработать MemoryService (deleteFact/updateFact + UNIQUE/хэш-дедуп) — НЕ миграция, а точечный фикс
└── НЕТ → задокументировать, что удаление только сырым SQL

Нужна ли синхронизация памяти между агентами?
├── ДА → sqlite-sync (Elastic 2.0 → коммерческая или cloud) — отдельный проект с лицензионным ревью
└── НЕТ → оставить локальную память

Нужны ли markdown-корпуса с чанкингом?
├── ДА → смотреть sqlite-memory (MIT, но C-ext + SQL-интерфейс из Node) — пилот вне prod
└── НЕТ → текущая модель «атомарных фактов» уже правильная для этого бота
```

## 20. Рекомендация (по измеренным данным)

1. **Не мигрировать.** Ни один кандидат не окупает стоимость замены при текущем масштабе (prod-память пуста; пиковые нагрузки не измерены).
2. **Точечные фиксы по приоритету:**
   - P0: включить HTTP-эмбеддинги в проде (код готов) и перемерить semantic recall.
   - P1: recency-коэффициент в RRF (лечит 50/50 противоречий).
   - P1: deleteFact/updateFact + дедупликация по контент-хэшу (как у sqlite-memory — но у себя).
   - P2: try/catch вокруг vec-запроса (изолировать битые BLOB) и защита `JSON.parse` metadata.
   - P2: смягчить AND-конъюнкцию FTS (fallback на OR/токены с большей частотой), чтобы естественно-языковые запросы не давали 0.
3. **Отсроченно:** при >100k записей — пересмотреть индекс (дерево решений §19).

## 21. План миграции

**Не составляется — миграция не обоснована** измеренными данными (см. §20.1). План появится только если владелец по дереву §19 выберет ветку, требующую замены компонента (например, >100k + sqlite-vector/ANN), и только после лицензионного решения.

## 22. Что НЕ менять

- Схему `facts/messages/insights` и триггеры FTS — они целостны и проходят все тесты целостности.
- WAL + synchronous=1 + busy_timeout=5000 — конфигурация уже корректна.
- Гибрид RRF k=60 как таковой — замена фьюжн-слоя не требуется; улучшения — аддитивные (recency-член, пороги).
- sqlite-vec (MIT/Apache-2.0) — замена на Elastic-лицензированные расширения юридически ухудшит позицию.
- `HashingEmbeddingService` — оставить как офлайн-фолбэк (работает, детерминирован, без сети).
