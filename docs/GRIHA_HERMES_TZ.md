# ТЗ: Полный перенос принципов Hermes в Гришу

**Цель:** сделать Telegram-агента «Гриша» таким же быстрым, чётким, «умным» (память + обучение) и стабильным, как Hermes — **не ломая** текущее поведение Гриши (изоляция сессий, ACL, группы, память, скиллы, cron).

**Дата:** 2026-09-13
**Стек Гриши:** TypeScript (Node + tsx), фреймворк `@earendil-works/pi-coding-agent`
**Стек Hermes:** Python, собственный агент-кор

---

# Часть 1. Диагностика и срочный фикс

## 1.0. Уточнение по языку

Гриша **уже написан на TypeScript** (`.ts`/`tsx`), Hermes — на Python. «Переделывать на TypeScript» не нужно: переносим только **принципы/логику**, реализация — на TypeScript внутри кодовой базы Гриши.

## 1.1. Резюме

| Проблема | Причина | Решение |
|---|---|---|
| «Слишком долго обрабатываю запрос» | `deepseek-v4-pro` — reasoning-модель; Гриша шлёт `reasoning: false`, из-за чего pi **не отправляет** `thinking` в API → DeepSeek включает рассуждения без лимита | `reasoning: true` → pi шлёт `thinking:{type:"disabled"}` |
| «Быстро и чётко» | Hermes **явно управляет** thinking + стабилизирует системный промпт | перенос механизма thinking + prompt caching |
| «Умный и учится» | У Гриши уже есть память/скиллы/профиль | переносить почти нечего — только не сломать |

## 1.2. Корневая причина (проверено по коду)

`apps/agent/src/utils/bootstrap/provider-bootstrap.ts` → `makeModel()` (строка 28):

```ts
reasoning: false,   // ← виновник
```

Проверено в `node_modules/@earendil-works/pi-ai/dist/api/openai-completions.js` (строка 681):

```js
else if (compat.thinkingFormat === "deepseek" && model.reasoning) {
    if (options?.reasoningEffort) params.thinking = { type: "enabled" };
    else if (model.thinkingLevelMap?.off !== null) params.thinking = { type: "disabled" };
}
```

Ветка срабатывает **только при `model.reasoning === true`**. При `false` pi не шлёт `thinking`, а DeepSeek V4 по умолчанию включает thinking (документировано в коде Hermes: `plugins/model-providers/deepseek/__init__.py`).

**Замеры API:**
| Запрос | reasoning-токенов | Время |
|---|---|---|
| без параметра | 377 | 3+ сек (в агенте — минуты) |
| `thinking:{type:"disabled"}` | 0 | 1.1 сек |
| `deepseek-chat` (V3) | 0 | 0.9 сек |

## 1.3. Срочный фикс (одна строка)

```ts
// provider-bootstrap.ts, makeModel()
reasoning: true,   // было false
```

После этого pi шлёт `thinking:{type:"disabled"}` → ответ ~1 сек. Правка общая для всех моделей (`v4-pro`, `v4-flash`, `v4-flash-vision-exp`), поэтому Vision тоже перестаёт «думать» — для OCR это и нужно.

# Часть 2. Как устроен Hermes — детальный разбор по осям

Ниже — механизмы, которые делают Hermes «быстрым, чётким и стабильным». Для каждой оси: **как у Hermes → как у Гриши сейчас → что сделать**.

---

## 2.1. Управление моделью и reasoning

**Hermes.** Отдельный профиль провайдера (`plugins/model-providers/deepseek/__init__.py`, класс `DeepSeekProfile.build_api_kwargs_extras`) для каждой модели явно шлёт:
```json
{ "thinking": { "type": "enabled" | "disabled" },
  "reasoning_effort": "low|medium|high|max" }   // только если thinking=enabled
```
Логика: `deepseek-v4-*` и `deepseek-reasoner` — thinking-модели; `deepseek-chat` (V3) — нет. Если `reasoning_config.enabled=False` → `thinking:{type:"disabled"}`. Уровень усилия по умолчанию берётся из `agent.reasoning_effort` (у меня `medium`).

**Гриша.** Есть только поле `reasoning: false` в каталоге — оно не доходит до API. Параметр `thinking` не шлётся вообще.

**Что сделать.** §1.3 (разовый фикс). Для продвинутого сценария (оставить reasoning для тяжёлых задач) — прокинуть `reasoningEffort` в опции хода (см. Вариант 2 в Части 3).

---

## 2.2. Системный промпт — трёхуровневая сборка

**Hermes.** Файл `agent/system_prompt.py`, функция `build_system_prompt_parts()` собирает промпт из **трёх слоёв**, склеенных `\n\n`:

1. **`stable`** (неизменный на всю сессию): идентичность (`SOUL.md` / `DEFAULT_AGENT_IDENTITY`), гайдансы по инструментам, **скиллы**, environment-hints, platform-hints, **tool-use enforcement**, контекст проекта, режим (dev/secretary), профиль.
2. **`context`**: пользовательский `system_message` + контекстные файлы (`AGENTS.md`, `.cursorrules` и т.п.) из рабочей директории.
3. **`volatile`** (меняется между сессиями, НО не между ходами): **снимок памяти**, **профиль USER.md**, блок внешней памяти, строка времени.

```python
# упрощённо:
def build_system_prompt(agent, system_message=None):
    parts = build_system_prompt_parts(agent, system_message)
    return "\n\n".join(parts["stable"], parts["context"], parts["volatile"])
```

**Зачем это:** стабильные блоки впереди → у upstream-провайдера **греется префикс-кэш** (см. 2.3). Изменчивое (память/время) — в конце, чтобы не инвалидировать кэш.

**Гриша.** Промпт собирает pi (ядро агента) + расширения. Есть `STYLE_BLOCK` (подмешивается в каждый ход в `TelegramSessionPool.runPrompt`), скиллы инжектятся core-agent, память — через расширения. Явного разделения stable/context/volatile и гарантии «не пересобираем mid-session» — **не видно**.

**Что сделать.**
1. Явно разделить сборку промпта на стабильную (идентичность + скиллы + гайдансы) и изменчивую (память + профиль + время) части.
2. Собирать системный промпт **один раз на сессию**, кэшировать, пересобирать только после сжатия контекста.
3. `STYLE_BLOCK` и `rulesContext` держать в начале **пользовательского** сообщения (не трогая системный промпт), чтобы не ломать кэш.

---

## 2.3. Prompt caching (стабильность префикса)

**Hermes.** Жёсткий принцип (из `AGENTS.md`): *«Per-conversation prompt caching is sacred»*. Системный промпт строится **один раз** и кэшируется на `agent._cached_system_prompt`; пересборка — **только** после сжатия контекста. Таймстамп — **только дата** (`strftime('%A, %B %d, %Y')`), а не минуты, чтобы строка была byte-stable весь день. Точное время модель берёт инструментом, когда нужно.

```python
timestamp_line = f"Conversation started: {now.strftime('%A, %B %d, %Y')}"
```

**Зачем:** DeepSeek/OpenAI/Anthropic кэшируют повторяющийся префикс. Если системный промпт байт-в-байт одинаков на каждом ходу — повторные ходы стоят дешевле и идут быстрее.

**Гриша.** Не видно явного механизма стабилизации. Если pi пересобирает промпт каждый ход (или подмешивает таймстамп с минутами) — кэш инвалидируется.

**Что сделать.**
1. Системный промпт собирать один раз на сессию и не менять между ходами.
2. Таймстамп/строку модели держать с точностью до даты (или вообще вынести в пользовательский слой).
3. Не подмешивать в системный промпт ничего, что меняется от хода к ходу.

---

## 2.4. Память (факты + профиль)

**Hermes.** Встроенная память (`agent/memory_manager.py`, `memory/`): хранит **факты** и **профиль пользователя** (`USER.md`). Инжектится в **volatile**-слой через `format_for_system_prompt("memory")` и `format_for_system_prompt("user")`. Есть внешние провайдеры памяти (Honcho, Mem0 и др.) через плагины `plugins/memory/`. Лимиты из `config.yaml`:

```yaml
memory:
  memory_enabled: true
  user_profile_enabled: true
  write_approval: false      # писать память без подтверждения
  memory_char_limit: 2200    # лимит блока памяти в промпте
  user_char_limit: 1375      # лимит профиля
  flush_min_turns: 6         # флеш в диск каждые N ходов
  nudge_interval: 10         # напоминание записывать важное
```

**Гриша.** Уже богаче: SQLite + FTS5 + вектор (`sqlite-vec`) + эмбеддинги, гибридный поиск (RRF), `memory_add`/`memory_search`, UserProfile + Client Notes + авто-извлечение фактов (Phase 4, 9). **Переносить нечего.**

**Что сделать.** Ничего. Но обратить внимание на два параметра Hermes, которых у Гриши может не быть:
- **`write_approval`** — писать ли память без явного подтверждения (у Гриши проверь: авто-извлечение фактов должно быть review-gated, как в Phase 9).
- **лимиты символов** памяти/профиля в промпте — чтобы блок памяти не раздувал контекст.

---

## 2.5. Скиллы (процедурная память)

**Hermes.** Скиллы — каталог `~/.hermes/skills/<категория>/<skill>/SKILL.md` (YAML frontmatter: name, description + markdown-тело). Обнаруживаются и **инжектятся в stable-слой** через `build_skills_system_prompt()`. Доступ: `skills_list`, `skill_view`, `skill_manage`. Фоновая курация — `curator` (устаревшие скиллы чистит/архивирует).

**Гриша.** Уже есть: `packages/skills/skills/core/SKILL.md` + инжект через core-agent (`discoverSkills`, `formatSkillsForPrompt`). **Переносить нечего.**

**Что сделать.** Ничего. Проверить только, что скиллы инжектятся в **стабильную** часть промпта (не пересобираются каждый ход).

---

## 2.6. Обучение (авто-извлечение)

**Hermes.** Память пополняется из хода: `sync_turn(user, asst)` после каждого хода + `on_session_end` + `on_pre_compress` (извлечение перед сжатием контекста). Профиль USER.md обновляется отдельно. Куратор фоново убирает устаревшее.

**Гриша.** Phase 9: UserProfile + Client Notes + **авто-извлечение фактов/предпочтений/заметок**, авто-улучшение скиллов (review-gated). **Переносить нечего.**

**Что сделать.** Ничего. Убедиться, что авто-извлечение review-gated (LLM-предложение → подтверждение/очередь → apply), а не бесконтрольно пишет в память.

---

## 2.7. Tool-use enforcement (принуждение к инструментам)

**Hermes.** В stable-слой инжектится гайданс `TOOL_USE_ENFORCEMENT_GUIDANCE` — модель **обязана вызывать инструменты, а не описывать намерения**. Управляется `config.yaml → agent.tool_use_enforcement` (`auto`/`true`/`false`/список моделей). Отдельные операционные гайдансы по семействам моделей (Gemini/GPT/Grok) — «проверяй перед правкой», «не фабрикуй вывод».

**Гриша.** Явного аналога не видно. Это одна из причин, почему Hermes «делает, а не рассказывает».

**Что сделать.** Добавить в стабильную часть промпта короткий гайданс: «вызывай инструменты для реальных действий; не описывай намерение — выполняй; не фабрикуй результат, если путь заблокирован — скажи прямо».

---

## 2.8. Сжатие контекста

**Hermes.** `agent/context_compressor.py` — при превышении порога (60% окна) делает **lossy-саммаризацию** старой части диалога. Параметры из `config.yaml`:
```yaml
compression:
  enabled: true
  threshold: 0.6        # сжимать при 60% окна
  target_ratio: 0.15    # сохранить 15% как саммари
  protect_last_n: 20    # не трогать последние 20 сообщений
  protect_first_n: 3    # не трогать первые 3
```
После сжатия системный промпт **пересобирается** (`invalidate_system_prompt`) — это единственная разрешённая причина пересборки.

**Гриша.** Не проверено. Если длинная сессия Telegram растёт без сжатия — контекст переполняется и деградирует.

**Что сделать.** Проверить, есть ли у pi/Griha механизм сжатия. Если нет — добавить саммаризацию старого хвоста при достижении порога, с сохранением последних N сообщений и пересборкой системного промпта.

---

## 2.9. Стиль ответа / persona

**Hermes.** Идентичность — `SOUL.md` (или `DEFAULT_AGENT_IDENTITY`) в stable-слое + personality (`kawaii`/`concise`/`technical` и др.) из `config.yaml → display.personality`. Каждая personality — короткая системная инструкция.

**Гриша.** `STYLE_BLOCK` (`length: short, verbosity: low`) подмешивается в **каждый** ход. Есть `core/SKILL.md` с секцией «Response style (Telegram)».

**Что сделать.** Ничего. `STYLE_BLOCK` уже решает задачу краткости. (Опционально: вынести стиль в стабильную часть, а не в каждый ход — но текущий вариант тоже работает.)

---

## 2.10. Вспомогательные модели (vision)

**Hermes.** `auxiliary.*` в config.yaml — отдельные модели для побочных задач: vision, web_extract, compression, triage и др. Каждая со своим provider/model/api_key/base_url. Картинки **предобрабатываются** vision-моделью, описание подставляется в сообщение.

**Гриша.** Уже реализовано: `models.vision` → `deepseek-v4-flash-vision-exp` + инструмент `analyze_image` + `downloadTelegramFileAsBase64` (file_id → байты). **Переносить нечего.**

---

## 2.11. Ограничения памяти и флеш-политика

**Hermes.** Память флешится в диск каждые `flush_min_turns=6` ходов; `nudge_interval=10` — напоминание записывать важное; `write_approval=false` — писать без подтверждения. Лимиты символов не дают блоку памяти раздуть промпт.

**Гриша.** Память в SQLite (персистентна по своей природе). Проверить: есть ли лимит на размер блока памяти в промпте и политика авто-записи.

# Часть 6. Риски

1. **Вариант 1 (thinking off)** — на сложных многошаговых задачах качество может быть чуть ниже. При необходимости — `reasoning_effort: "medium"` точечно для тяжёлых веток.
2. **Правка кода** в `provider-bootstrap.ts` — по правилам применяется только после явного «делай».
3. **reasoning_content echo** — при включённом reasoning DeepSeek требует эхо поля в следующих ходах (HTTP 400). Вариант 1 (thinking off) проблемы не имеет.
4. **Prompt caching в pi** — если pi сам пересобирает системный промпт каждый ход, добиться byte-stability сложнее; тогда выигрыш от кэша частичный, но сам фикс reasoning (§1.3) от этого не зависит.
5. **Сжатие контекста** — если его нет в pi, внедрение саммаризации — отдельная нетривиальная задача (не блокирует Этап A).
